## ۱. مسئله‌ای که حل می‌کند

پیش از این تغییر، قراردادهای شما یک تناقض داخلی داشتند.

قرارداد ظرفیت فیزیکی لینک را **حساب می‌کرد** — با SINR واقعی و فرمول شانون —
و در رکورد می‌نوشت. مثلاً برای دستگاهی در فاصلهٔ ۲۰۱۱ متر:

```
capacityBps = 77,600,000     ← ۷۷.۶ مگابیت بر ثانیه
```

و در همان تراکنش، پارامتر `bandwidth` را که کاربر فرستاده بود، **بدون هیچ
مقایسه‌ای** ذخیره می‌کرد. اگر کاربری عدد ۹۹۹۹۹۹ می‌فرستاد، ثبت می‌شد.

دو عدد در یک رکورد کنار هم می‌نشستند و هرگز با هم حرف نمی‌زدند.

مشکل عمیق‌تر این بود که آن ۷۷.۶ مگابیت **ظرفیت کل سلول** بود، نه سهم این
موجودیت. اگر دویست دستگاه به همان سلول وصل باشند، هیچ‌کدام ۷۷ مگابیت نمی‌گیرند.
عدد از نظر فیزیکی درست بود ولی از نظر شبکه‌ای بی‌معنا.

انرژی هم همین وضع را داشت: `RecordEnergy(entityID, energy, x, y)` عددی می‌گرفت
و می‌نوشت. هیچ بودجه‌ای، هیچ کاهشی، هیچ قیدی.

**در یک جمله: منابع ثبت می‌شدند، مدیریت نمی‌شدند.**

## ۲. نگاشت معادلات مقاله

مقاله دقیقاً همین سه چیز را مدل می‌کند. جدول زیر نشان می‌دهد چه چیزی از کجا
آمده است:

| مقاله | معادله | پیاده‌سازی |
|---|---|---|
| پهنای باند کاربر `w_n0`, `w_nm` | — | `cfg.RequestHz` از استخر سلول |
| نرخ دست‌یافتنی `R̂ = w·log2(1+SNR)` | (۴)، (۵) | `ShannonBps(RequestHz, SINR)` |
| اندازهٔ داده `D = a₁ + a₂q` | (۶) | `cfg.PayloadBits` |
| زمان ارسال `t = D/R̂` | (۱۰) | `TransmitTimeMicroS` |
| انرژی `e = P·D/R̂` | (۱۱) | `TransmitEnergyMicroJ` |
| قید `C3: e ≤ E_max` | (۱۵) | بررسی بودجه در `admit` |

و مقادیر پیش‌فرض هم از جدول I مقاله برداشته شده‌اند:

| پارامتر | مقاله | پیش‌فرض شما |
|---|---|---|
| توان ارسال کاربر `P_n` | ۲۳ dBm | ۲۳۰۰۰ milli-dBm |
| بیشینه انرژی `E_max` | ۵ ژول | ۵٬۰۰۰٬۰۰۰ µJ |
| سربرگ بلاک `a₁` | ۶۰۸ بیت | جزو ۳۸۰۸ بیت |
| هر nonce `a₂` | ۳۲ بیت | ۱۰۰ × ۳۲ = ۳۲۰۰ بیت |
| نمای افت مسیر `α` | ۳ | ۳.۰ |

**یک تفاوت مهم:** در مقاله `D` اندازهٔ دادهٔ استخراج PoW است و `q` تعداد nonce.
در فابریک استخراجی وجود ندارد، پس `PayloadBits` صرفاً حجم دادهٔ ارسالی است.
مقدار پیش‌فرض را برابر همان `a₁ + 100·a₂` مقاله گذاشتم تا مقیاس قابل مقایسه
بماند، ولی معنایش عوض شده و در گزارش باید ذکر شود.

## ۳. سازوکار اول: استخر طیف

### چه چیزی اضافه شد

هر آنتن یک فیلد جدید گرفت:

```go
type Antenna struct {
    ...
    BandwidthHz  int64   // ۲۰ مگاهرتز — کل باند سلول
    AllocatedHz  int64   // چقدرش تعهد شده  ← جدید
}
```

### قید

در `admit`، پیش از پذیرش:

```go
if cfg.TrackBandwidth && best.AllocatedHz+cfg.RequestHz > best.BandwidthHz {
    return rep, best, fmt.Errorf(
        "cell %s has no spectrum left: %d Hz free, %d Hz requested",
        best.AntennaID, best.BandwidthHz-best.AllocatedHz, cfg.RequestHz)
}
```

و پس از پذیرش، `AllocatedHz` افزایش می‌یابد و رکورد آنتن ذخیره می‌شود.
`Release` آن را برمی‌گرداند.

### رفتار عملی

با پیش‌فرض ۱۰۰ کیلوهرتز به‌ازای هر موجودیت، هر سلول ۲۰ مگاهرتزی دقیقاً ۲۰۰
موجودیت جا می‌دهد. شبیه‌سازی با ۳۰۰۰ موجودیت:

```
پذیرفته: 1535 | رد به‌دلیل نبود طیف: 1451

antenna-1  20.0/20.0 MHz (100%)  200 موجودیت
antenna-2  20.0/20.0 MHz (100%)  200 موجودیت
...
antenna-8  13.5/20.0 MHz  (68%)  135 موجودیت
```

هفت سلول کاملاً پر شدند و یکی — که در گوشهٔ نقشه است و کمتر موجودیت به آن
نزدیک است — ۶۸٪ اشغال ماند. این همان **ازدحام نابرابر** است که الگوریتم ۲
مقاله برای حلش طراحی شده.

## ۴. سازوکار دوم: نرخ روی سهم

### تغییر یک‌خطی که همه‌چیز را عوض می‌کند

پیش از این:

```go
CapacityBps: ShannonBps(best.BandwidthHz, sinr)    // کل سلول
```

حالا:

```go
rateBandwidth := best.BandwidthHz
if cfg.TrackBandwidth {
    rateBandwidth = cfg.RequestHz                   // سهم این موجودیت
}
capacity := ShannonBps(rateBandwidth, sinr)
```

### تفاوت در عمل

با SINR یکسان، عددی که گزارش می‌شود دویست برابر فرق می‌کند:

| موجودیت | فاصله | SINR | ظرفیت کل سلول | ظرفیت سهم ۱۰۰kHz |
|---|---|---|---|---|
| dev-1 | ۲۳۶۷m | ۸.۹ dB | ۶۲.۳ Mbps | ۰.۳۱۲ Mbps |
| dev-2 | ۲۴۴۶m | ۱۵.۲ dB | ۱۰۲.۱ Mbps | ۰.۵۱۰ Mbps |
| dev-3 | ۴۲۷۶m | ۰.۰ dB | ۱۹.۹ Mbps | ۰.۰۹۹ Mbps |

ستون آخر چیزی است که موجودیت واقعاً می‌گیرد. ستون قبلی صرفاً می‌گفت لینک از
نظر فیزیکی چه توانی دارد اگر تنها کاربر سلول بود.

### چرا این برای انرژی حیاتی است

انرژی از نرخ می‌آید (`e = P·D/R`). اگر نرخ را کل سلول بگیرید، زمان ارسال
دویست برابر کوتاه‌تر و انرژی دویست برابر کمتر محاسبه می‌شود — عددی که هیچ
ربطی به واقعیت ندارد. **بدون این تغییر، بودجهٔ انرژی بی‌معنا بود.**

## ۵. سازوکار سوم: بودجهٔ انرژی

### ساختار داده

```go
type EnergyBudget struct {
    EntityID        string
    TotalMicroJ     int64   // ۵ ژول = ۵٬۰۰۰٬۰۰۰ µJ
    RemainingMicroJ int64
    SpentMicroJ     int64
    TxCount         int64
    Timestamp       string
}
```

کلیدش `~NRG:<entityID>` است — یعنی **هر موجودیت رکورد خودش را دارد**. این
انتخاب معماری در بخش ۷ توضیح داده می‌شود و مهم‌ترین نکتهٔ این سند است.

### محاسبه

```
t = PayloadBits × 10⁶ / capacityBps          میکروثانیه
e = MicroWatt(TxPower) × t / 10⁶             میکروژول
```

با `TxPower = 23 dBm` که ۱۹۹٬۴۲۴ میکرووات است.

### قید

```go
if budget.RemainingMicroJ < rep.EnergyMicroJ {
    return rep, best, fmt.Errorf(
        "%s has %d µJ left but the transmission costs %d µJ",
        entityID, budget.RemainingMicroJ, rep.EnergyMicroJ)
}
```

دقیقاً معادل قید `C3` مقاله.

### رفتار عملی

باتری اولین بار که موجودیتی تراکنش می‌فرستد به‌طور خودکار با شارژ کامل ساخته
می‌شود، پس نیازی به مرحلهٔ آماده‌سازی جدا نیست.

| موجودیت | فاصله | نرخ | زمان | انرژی | تراکنش تا تخلیه |
|---|---|---|---|---|---|
| dev-2 | ۲۴۴۶m | ۰.۵۱۰ Mbps | ۷.۵ms | ۱۴۸۸ µJ | ۳۳۶۰ |
| dev-1 | ۲۳۶۷m | ۰.۳۱۲ Mbps | ۱۲.۲ms | ۲۴۳۶ µJ | ۲۰۵۲ |
| dev-3 | ۴۲۷۶m | ۰.۰۹۹ Mbps | ۳۸.۳ms | ۷۶۴۷ µJ | ۶۵۳ |
| dev-6 | ۵۷۳۰m | ۰.۰۶۸ Mbps | ۵۵.۷ms | ۱۱۱۰۲ µJ | ۴۵۰ |

زنجیرهٔ علّی روشن است: **دورتر → SINR کمتر → نرخ کمتر → زمان بیشتر → انرژی
بیشتر → تخلیهٔ زودتر.** دستگاه لبهٔ سلول هفت برابر زودتر از دستگاه نزدیک باتری
خالی می‌کند.

این همان اثری است که مقاله در تابع هزینه‌اش (معادله ۱۳) بین تأخیر و انرژی
وزن‌دهی می‌کند.

### نکتهٔ عملی برای بنچمارک

در بنچمارک هر تراکنش شناسهٔ یکتا دارد (`bench-1`، `bench-2`، …)، پس هر تراکنش
یک باتری تازه می‌سازد و **تخلیه دیده نمی‌شود**. برای مشاهدهٔ تخلیه باید همان
موجودیت را بارها صدا بزنید — با `EnergyOf` می‌توانید وضعیتش را ببینید.

## ۶. مسیر کامل یک تراکنش

با هر دو سازوکار روشن، هر فراخوانی این مسیر را طی می‌کند:

```
۱. اعتبارسنجی ورودی      مختصات عدد صحیح؟ شناسه خالی نیست؟
۲. بارگذاری پیکربندی      خواندن ~CFG
۳. بررسی بذر             بذر آرگومان با بذر چیدمان می‌خواند؟
۴. بارگذاری آنتن‌ها       خواندن ~ANT:* (۸ رکورد)
۵. ارزیابی رادیویی
     برای هر ۸ آنتن:  فاصله → افت مسیر → سایه‌فرسایی → RSSI
     قوی‌ترین = سلول سرویس‌دهنده، بقیه = تداخل
     SINR = جمع خطی تداخل و نویز
     نرخ = شانون روی سهم پهنای باند
     زمان = payload / نرخ
     انرژی = توان × زمان
۶. قید پوشش              SINR ≥ آستانه؟
۷. قید ظرفیت اتصال       سلول جا دارد؟          (اختیاری)
۸. قید طیف               باند آزاد کافی است؟     (اختیاری)
۹. قید انرژی             باتری کفاف می‌دهد؟      (اختیاری)
─────────── تا اینجا فقط خواندن ───────────
۱۰. برداشت طیف           AllocatedHz += سهم  → نوشتن رکورد سلول
۱۱. برداشت انرژی         Remaining -= هزینه  → نوشتن رکورد موجودیت
۱۲. نوشتن رکورد اصلی     PutState(entityID, record)
```

هر یک از مراحل ۶ تا ۹ می‌تواند تراکنش را رد کند، و **هر کدام پیام خطای متفاوتی
می‌دهد** — پس وقتی تراکنشی رد شد، دقیقاً می‌دانید کدام منبع تمام شده.

رکورد نهایی حالا این فیلدها را هم دارد:

```json
{
  "servingCell": "antenna-3",
  "sinrMilliDb": 11370,
  "capacityBps": 388000,
  "grantedHz": 100000,
  "txTimeMicroS": 9814,
  "energyMicroJ": 1958
}
```

## ۷. تفاوت همزمانی — مهم‌ترین یافته

اینجا جایی است که پیاده‌سازی شما چیزی نشان می‌دهد که مقاله نمی‌تواند.

### دو منبع، دو الگوی نوشتن

**طیف روی رکورد سلول است.** فقط ۸ آنتن وجود دارد، پس هر تخصیص یک
خواندن-تغییر-نوشتن روی یکی از تنها ۸ کلید است.

**انرژی روی رکورد موجودیت است.** هر موجودیت کلید خودش را دارد، پس دو تراکنش
از دو موجودیت متفاوت هرگز به یک کلید دست نمی‌زنند.

### چرا این اهمیت دارد

فابریک مجموعهٔ خواندن-نوشتن را **پس از** ترتیب‌دهی اعتبارسنجی می‌کند. اگر چند
تراکنش در یک بلاک همان کلید را با همان نسخه بخوانند، اولی کامیت می‌شود و بقیه
با `MVCC_READ_CONFLICT` رد می‌شوند.

پیش‌بینی کمّی:

| نرخ | تراکنش در بلاک | روی شلوغ‌ترین سلول | نرخ موفقیت با ردیابی طیف |
|---|---|---|---|
| ۲۰ tps | ۴۰ | ~۸ | حدود ۲۰٪ |
| ۵۰ tps | ۱۰۰ | ~۲۰ | حدود ۸٪ |
| ۱۰۹ tps | ۲۱۸ | ~۴۳ | زیر ۴٪ |

**در حالی که ردیابی انرژی هیچ افتی نباید بدهد** — چون کلیدها یکتا هستند.

### چرا در مقاله دیده نمی‌شود

در MATLAB، خواندن و نوشتن `Σ X_j` رایگان و آنی است. مقاله در بند پایانی بخش IV
اعتراف می‌کند که «تخصیص بهینه از نظر توازن بار به‌دست نمی‌آید» ولی دلیلش را به
ترتیب اجرای الگوریتم نسبت می‌دهد، نه به هزینهٔ دسترسی به حالت مشترک.

**شما می‌توانید نشان دهید که روی یک دفتر توزیع‌شدهٔ واقعی، حالت مشترک خودش
گلوگاه است** — و این محدودیتی است که هر سامانهٔ مدیریت منابع مبتنی بر بلاکچین
با آن روبه‌روست، نه فقط این پیاده‌سازی.

## ۸. پیکربندی و استفاده

### روشن کردن

هر دو سازوکار **پیش‌فرض خاموش‌اند**، پس بنچمارک‌های موجود شما دست‌نخورده
می‌مانند.

```bash
docker exec -e CORE_PEER_LOCALMSPID=org1MSP \
  -e CORE_PEER_MSPCONFIGPATH=/etc/hyperledger/fabric/admin-msp \
  -e CORE_PEER_ADDRESS=peer0.org1.example.com:7051 \
  peer0.org1.example.com peer chaincode invoke \
  -o orderer.example.com:7050 -C datachannel -n LocationBasedBandwidth \
  --peerAddresses peer0.org1.example.com:7051 \
  -c '{"function":"SetResources","Args":["on","on","100000","5000000","23000","3808"]}'
```

آرگومان‌ها به‌ترتیب: ردیابی طیف، ردیابی انرژی، سهم به هرتز، بودجه به میکروژول،
توان به milli-dBm، و حجم payload به بیت.

برای خاموش کردن یکی: `["off","on","","","",""]` — رشتهٔ خالی یعنی مقدار فعلی
حفظ شود.

### پرس‌وجوها

```bash
# اشغال طیف هر سلول
-c '{"function":"SpectrumStatus","Args":[]}'

# باتری یک موجودیت
-c '{"function":"EnergyOf","Args":["dev-1"]}'

# شارژ مجدد
-c '{"function":"RechargeEntity","Args":["dev-1"]}'

# پیش‌بینی بدون نوشتن — سلول، SINR، نرخ، زمان، انرژی
-c '{"function":"ServingCell","Args":["dev-1","3000","4000"]}'
```

`ServingCell` مفیدترین ابزار تشخیص است: پیش از هر بنچمارک می‌توانید ببینید یک
موجودیت در موقعیت مشخص چه چیزی می‌گیرد، بدون اینکه چیزی بنویسید.

### انتخاب اندازهٔ سهم

سهم پهنای باند یک بده‌بستان مستقیم می‌سازد:

| سهم | نرخ | زمان | انرژی | تراکنش تا تخلیه | موجودیت در سلول |
|---|---|---|---|---|---|
| ۴۰ kHz | ۰.۱۵۵ Mbps | ۲۴.۶ms | ۴۸۹۶ µJ | ۱۰۲۱ | ۵۰۰ |
| ۱۰۰ kHz | ۰.۳۸۸ Mbps | ۹.۸ms | ۱۹۵۸ µJ | ۲۵۵۳ | ۲۰۰ |
| ۲۰۰ kHz | ۰.۷۷۵ Mbps | ۴.۹ms | ۹۷۹ µJ | ۵۱۰۷ | ۱۰۰ |
| ۱ MHz | ۳.۸۷۷ Mbps | ۱.۰ms | ۱۹۵ µJ | ۲۵۶۴۱ | ۲۰ |

سهم بزرگ‌تر یعنی هر موجودیت سریع‌تر و کم‌مصرف‌تر است، ولی تعداد کمتری در سلول
جا می‌شوند. **این دقیقاً همان بده‌بستانی است که مقاله در تابع هزینه‌اش وزن‌دهی
می‌کند** و حالا قابل اندازه‌گیری است.

مقادیر ۴۰ و ۱۶۰ کیلوهرتز مقاله در همین محدوده‌اند، پس اگر بخواهید نتایج را با
آن مقاله مقایسه کنید، سهم را در همان بازه بگذارید.

## ۸ــ۵. وضعیت کامل تخصیص منابع

این بخش هر چیزی را که در کد فعلی وجود دارد فهرست می‌کند، تا بدانید چه در
اختیار دارید.

### پنج قید مستقل

هر تراکنش پذیرش، تا پنج بررسی را از سر می‌گذراند. هر کدام مستقلاً قابل
روشن/خاموش کردن است:

| # | قید | پیش‌فرض | با چه چیزی روشن می‌شود |
|---|---|---|---|
| ۱ | پوشش (SINR ≥ آستانه) | همیشه روشن | `SetPropagation` آستانه را عوض می‌کند |
| ۲ | ظرفیت اتصال | خاموش | `SeedNetwork` با `maxCapacity > 0` |
| ۳ | طیف آزاد | خاموش | `SetResources` با `trackBandwidth = on` |
| ۴ | بودجهٔ انرژی | خاموش | `SetResources` با `trackEnergy = on` |
| ۵ | موجودی مالی | خاموش | `SetEconomy` یا `SetMarket` |

قید اول همیشه فعال است چون بدون آن مدل رادیویی معنا ندارد. چهار تای دیگر عمداً
خاموش‌اند تا بنچمارک پایه چیز دیگری را نسنجد.

### آنچه هر آنتن نگه می‌دارد

```go
type Antenna struct {
    AntennaID       string   // antenna-1 تا antenna-8
    X, Y            int64    // موقعیت، متر
    TxPowerMilliDbm int64    // 46000 = 46 dBm
    GainMilliDb     int64    // 15000 = 15 dBi
    FreqMHz         int64    // 3500
    BandwidthHz     int64    // 20000000 = 20 MHz
    MaxCapacity     int64    // سقف اتصال؛ 0 = نامحدود
    UsedCapacity    int64    // اتصال‌های جاری
    AllocatedHz     int64    // طیف تعهدشده
    LoadFactor      int64    // ε در صدم؛ 100 = 1.0
    EarnedMicro     int64    // درآمد از پرداخت سرویس
}
```

سه فیلد آخر در دورهای بعدی اضافه شدند و هر کدام یک بُعد آزمایش می‌دهند:
`AllocatedHz` برای تخصیص طیف، `LoadFactor` برای شبکهٔ ناهمگن، `EarnedMicro`
برای اقتصاد.

### آنچه پیکربندی شبکه نگه می‌دارد

`NetworkConfig` بیست‌وچهار فیلد دارد، در پنج گروه:

**محیط رادیویی** — `Seed`، `GridSizeM`، `AntennaCount`،
`PathLossExponentMilli`، `ShadowSigmaMilliDb`، `NoiseFigureMilliDb`،
`MinSinrMilliDb`

**تخصیص منابع** — `TrackCapacity`، `TrackBandwidth`، `RequestHz`،
`TrackEnergy`، `EnergyBudgetMicroJ`، `TxPowerMilliDbm`، `PayloadBits`

**استراتژی تخصیص سلول** — `AssociationMode`، `LoadToleranceHundred`

**اقتصاد سرویس** — `TrackEconomy`، `PricePerKHzMicro`، `PricePerKbitMicro`،
`InitialBalanceMicro`

**بازار نظیربه‌نظیر** — `Stripes`، `PriceScale`، `RelayShareHundred`،
`WorkReward`

### توان ارسال — حالا مدیریت می‌شود

```
SetPower(antennaID, txPowerMilliDbm)
```

پیش از این `TxPowerMilliDbm` روی ۴۶ dBm ثابت بود و هیچ تابعی عوضش نمی‌کرد.
حالا مستقیماً در `RssiMilliDbm` استفاده می‌شود، پس تغییرش بلافاصله بر SINR و
پوشش اثر می‌گذارد:

| توان | SINR میانگین | خارج از پوشش |
|---|---|---|
| ۳۶ dBm | ۷.۱ dB | ۵.۰٪ |
| ۴۶ dBm | ۱۴.۴ dB | ۰.۰٪ |
| ۵۳ dBm | ۱۷.۵ dB | ۰.۰٪ |

محدوده: ۰ تا ۶۰۰۰۰ میلی‌dBm. زیر صفر ماکروسل کسی را سرویس نمی‌دهد؛ بالای
۶۰ dBm فراتر از حد مجاز مقرراتی است.

**بده‌بستان:** توان بیشتر پوشش را گسترش می‌دهد ولی تداخل همسایه‌های هم‌کانال را
هم بالا می‌برد. در جدول بالا این دیده نمی‌شود چون همهٔ سلول‌ها با هم تغییر
کردند؛ اگر فقط یکی را بالا ببرید، SINR بقیه بدتر می‌شود.

### کانال فرکانسی — حالا مدیریت می‌شود

```
SetChannel(antennaID, channelIndex, freqMHz)
ReuseChannels(channelCount)
```

پیش از این همهٔ آنتن‌ها روی ۳۵۰۰ MHz بودند و هر هفت همسایه تداخل حساب
می‌شدند. حالا `evaluate` فقط سلول‌های **هم‌کانال** را تداخل می‌شمارد:

```go
if i != pick && antennas[i].ChannelIndex == best.ChannelIndex {
    interferers = append(interferers, rssi[i])
}
```

اثرش بزرگ‌ترین تک‌تغییر در کیفیت رادیویی است:

| تعداد کانال | همسایهٔ هم‌کانال | SINR میانگین | نرخ میانگین |
|---|---|---|---|
| ۱ | ۷.۰ | ۴.۹ dB | ۰.۲۳۲ Mbps |
| ۲ | ۳.۰ | ۹.۱ dB | ۰.۳۴۲ Mbps |
| ۴ | ۱.۰ | ۱۴.۴ dB | ۰.۴۹۷ Mbps |
| ۸ | ۰.۰ | ۱۸.۱ dB | ۰.۶۱۳ Mbps |

با چهار کانال، SINR **۹.۵ دسی‌بل** بهتر می‌شود و نرخ بیش از دو برابر.

### تقسیم خودکار پهنای باند

`ReuseChannels(n)` حالا باند را هم تقسیم می‌کند. طیف مجوزدار یک بلوک ثابت
است؛ بازاستفاده آن را تقسیم می‌کند، نه اینکه به هر کانال یک بلوک کامل بدهد.

`TotalBandwidthHz` روی پیکربندی نگه داشته می‌شود تا فراخوانی‌های مکرر همان
باند اصلی را تقسیم کنند، نه چیزی که فراخوانی قبلی از قبل نصف کرده.

سه اثر هم‌زمان رخ می‌دهد:

| کانال | هر سلول | هم‌کانال | کف نویز | SINR | نرخ کاربر | ظرفیت سلول |
|---|---|---|---|---|---|---|
| ۱ | ۲۰.۰ MHz | ۷.۰ | −۹۴ dBm | ۵.۱ dB | ۰.۲۳۹ Mbps | ۲۰۰ کاربر |
| ۲ | ۱۰.۰ MHz | ۳.۰ | −۹۷ dBm | ۱۰.۰ dB | ۰.۳۶۷ Mbps | ۱۰۰ کاربر |
| ۴ | ۵.۰ MHz | ۱.۰ | −۱۰۰ dBm | ۱۷.۵ dB | ۰.۵۹۴ Mbps | ۵۰ کاربر |
| ۸ | ۲.۵ MHz | ۰.۰ | −۱۰۳ dBm | ۲۷.۷ dB | ۰.۹۲۰ Mbps | ۲۵ کاربر |

دو اثر به نفع SINR کار می‌کنند و یکی علیه ظرفیت:

۱. **تداخل کمتر** — همسایه‌های هم‌کانال از ۷ به ۰ می‌رسند
۲. **نویز کمتر** — هر نصف شدن پهنای باند، کف نویز را ۳ dB پایین می‌آورد
۳. **ظرفیت کمتر** — سلول باریک‌تر کاربر کمتری جا می‌دهد

### نتیجه‌ای که خلاف انتظار درآمد

اگر گذردهی **مجموع شبکه** را حساب کنید — نرخ هر کاربر ضربدر تعداد کاربر:

| کانال | نرخ کاربر | کاربر کل | گذردهی مجموع |
|---|---|---|---|
| ۱ | ۰.۲۳۷ Mbps | ۱۶۰۰ | **۳۸۰ Mbps** |
| ۲ | ۰.۳۵۹ Mbps | ۸۰۰ | ۲۸۷ Mbps |
| ۴ | ۰.۵۹۰ Mbps | ۴۰۰ | ۲۳۶ Mbps |
| ۸ | ۰.۹۲۳ Mbps | ۲۰۰ | ۱۸۵ Mbps |

**بیشینهٔ گذردهی مجموع در یک کانال است** — یعنی بازاستفاده کامل فرکانسی.

دلیلش در ریاضیات شانون است: ظرفیت **لگاریتمی** در SINR ولی **خطی** در پهنای
باند. بازاستفاده SINR را چند برابر می‌کند، ولی چون سود لگاریتمی است هرگز به
زیان خطی ناشی از نصف شدن باند نمی‌رسد.

پس بازاستفاده گذردهی مجموع را بالا نمی‌برد؛ **نرخ فردی و کیفیت لبهٔ سلول** را
بالا می‌برد. در شبکهٔ واقعی هم دقیقاً به همین دلیل استفاده می‌شود — تجربهٔ
کاربر لبه، نه ظرفیت کل.

این یک آزمایش خوب برای پایان‌نامه است: نموداری با دو محور که نشان دهد نرخ
فردی و گذردهی مجموع در جهت مخالف حرکت می‌کنند.

### قیدهای عملی

- تعداد کانال نمی‌تواند از تعداد سلول بیشتر باشد
- هر کانال دست‌کم ۲۰۰ کیلوهرتز
- اگر سلولی طیف تعهدشده بیش از عرض کانال جدید داشته باشد، تغییر رد می‌شود —
  اول `Release` کنید

```
SpectrumPlan()   →   طرح جاری: باند کل، تعداد کانال، و جای هر سلول
```

## ۹. آزمایش‌هایی که ممکن می‌شوند

### آزمایش A: هزینهٔ همزمانی حالت مشترک

**سؤال:** آیا محل نگهداری حالت — مشترک در برابر خصوصی — بر گذردهی اثر دارد؟

سه اجرای Caliper با تنظیمات یکسان روی `datachannel`:

۱. هر دو سازوکار خاموش (پایه)
۲. فقط انرژی روشن (کلید خصوصی به‌ازای هر موجودیت)
۳. فقط طیف روشن (کلید مشترک، ۸ تا)

**پیش‌بینی:** ۱ و ۲ تقریباً یکسان، ۳ فروپاشی. اگر این نتیجه بیاید، شما یک
اصل طراحی برای سامانه‌های مدیریت منابع روی بلاکچین ثابت کرده‌اید.

این قوی‌ترین آزمایش در این فهرست است.

### آزمایش B: اشباع طیف

**سؤال:** ظرفیت پذیرش شبکه چقدر است و چگونه پر می‌شود؟

طیف را روشن کنید و بنچمارکی با تعداد تراکنش بیش از ۱۶۰۰ اجرا کنید. نرخ رد را
بر حسب پیشرفت اجرا رسم کنید: در ابتدا صفر، سپس با پر شدن سلول‌های شلوغ‌تر
پله‌پله بالا می‌رود.

نکتهٔ ظریف: چون بار ورونوی نابرابر است، سلول‌ها هم‌زمان پر نمی‌شوند. منحنی رد
پلکانی خواهد بود نه صاف.

### آزمایش C: اندازهٔ سهم

**سؤال:** بهترین اندازهٔ سهم چیست؟

سهم را ۴۰ → ۱۰۰ → ۲۰۰ → ۱۰۰۰ کیلوهرتز عوض کنید و برای هرکدام تعداد موجودیت
پذیرفته‌شده و میانگین نرخ هر موجودیت را ثبت کنید. حاصل‌ضرب این دو تقریباً ثابت
می‌ماند — که خودش نکته‌ای دربارهٔ حفظ ظرفیت است.

### آزمایش D: تخلیهٔ باتری بر حسب فاصله

**سؤال:** موقعیت مکانی چقدر بر عمر باتری اثر دارد؟

چند موجودیت در فاصله‌های مختلف انتخاب کنید، هرکدام را مکرراً صدا بزنید و با
`EnergyOf` مصرف را دنبال کنید. شبیه‌سازی می‌گوید نسبت لبه به مرکز حدود هفت
برابر است.

این آزمایش گذردهی بلاکچین را نمی‌سنجد؛ رفتار شبکهٔ سلولی را می‌سنجد. برای فصلی
از پایان‌نامه که دربارهٔ مدل شبکه است، نه دربارهٔ کارایی دفتر.

### آزمایش E: محیط انتشار و انرژی

**سؤال:** محیط شهری چقدر گران‌تر از فضای باز است؟

`SetPropagation` را با نمای ۲.۰ و سپس ۳.۵ اجرا کنید و مصرف انرژی همان موجودیت‌ها
را مقایسه کنید. افت مسیر بیشتر یعنی SINR کمتر، نرخ کمتر، و انرژی بیشتر.

### چه چیزی هنوز ممکن نیست

**الگوریتم ۲ مقاله** — تخصیص بارآگاه — هنوز پیاده نشده. قرارداد وقتی سلول پر
است رد می‌کند؛ مقاله می‌گوید باید به سلول بعدی برود. این کار شدنی است و
مهم‌ترین گام بعدی برای الهام‌گیری از آن مقاله است.

توجه: پیاده‌سازی الگوریتم ۲ **الزاماً** حالت مشترک را می‌خواند، پس نتیجهٔ
آزمایش A پیش‌بینی می‌کند که چه هزینه‌ای خواهد داشت.
